3.6. Entity Instance Lifecycle

Any entity instance can be characterized as being in one of the following lifecycle states with respect to a given persistence context:

  • A new entity instance has no persistent identity and is not yet associated with any persistence context.

  • A managed entity instance is an instance with a persistent identity that is currently associated with a persistence context.

  • A detached entity instance is an instance with a persistent identity that is not (or no longer) associated with a persistence context.

  • A removed entity instance is an instance with a persistent identity, and associated with a persistence context, that is scheduled for removal from the database upon transaction commit.

Certain operations of EntityManager modify the lifecycle state of an entity instance. The following subsections describe the effect of such lifecycle operations.

3.6.1. Lifecycle Operations

The fundamental operations of an EntityManager are:

  • persist() to make a new entity persistent, as defined in Section 3.6.3,

  • remove(), to remove a persistent entity from the database, as defined in Section 3.6.4,

  • flush(), to force synchronization of pending modifications with the database, as defined in Section 3.6.6,

  • refresh(), to reload an entity from the database, as defined in Section 3.6.7,

  • detach(), to disassociate an entity from its persistence context, as defined in Section 3.6.8,

  • merge(), to copy the state of a detached instance into the persistence context, and

  • lock() to obtain a lock an entity instance or to upgrade the lock level currently held, as defined in Section 3.9.

The methods persist(), remove(), refresh(), detach(), and merge() are called lifecycle operations.

The cascade annotation element of a relationship modeling annotation, as defined in Section 2.11, specifies which lifecycle operations propagate to associated entities. Each lifecycle operation is identified by the corresponding member of the enumeration CascadeType.

public enum CascadeType {ALL, PERSIST, MERGE, REMOVE, REFRESH, DETACH}

The value cascade=ALL is equivalent to cascade={PERSIST, MERGE, REMOVE, REFRESH, DETACH}.

The cascade functionality is most typically used to model parent-child relationships. A closely related feature is orphan removal, which is defined below in Section 3.6.5.

Information about how lifecycle operations interact with transactions may be found below in Section 3.7.2.

3.6.2. Entity Instance Creation

An instance of an entity class may be created using the new operator. A newly instantiated instance is not considered persistent—​that is, it is not considered to represent a record in the database—​and the new instance is not associated with a persistence context. A new instance is not considered to have a well-defined persistent identity until it is made persistent.

3.6.3. Persisting an Entity Instance

A new instance becomes persistent when it is passed as an argument to the persist() method of EntityManager or when the persist operation cascades from another instance to the new instance.

Let e be an instance of an entity class. If e is passed as an argument to the persist() method of EntityManager, or if the persist operation is applied to e via cascade:

  • if e is a new entity, it becomes managed and a new record represented by e will be inserted into the database at or before transaction commit as a result of the flush operation specified below in Section 3.6.6;

  • if e is a managed entity already associated with the persistence context, e itself is ignored by the persist operation;

  • if e is a removed entity, it becomes managed; or

  • if e is a detached entity, either an EntityExistsException is thrown immediately, or an EntityExistsException or some other subtype of PersistenceException is thrown when the persistence context is flushed or when the transaction commits.

  • If e is new, managed, or removed, the persist operation is also applied to every entity t referenced by a relationship owned by e and annotated with the cascade element value cascade=PERSIST or cascade=ALL or mapped as such by the equivalent XML descriptor element.

Ordinarily, the persist operation assigns a persistent identity to the entity. If the primary key of the entity is a generated value, as defined by Section 11.2.23, the primary key is generated as part of the persist operation, and the generated value is made available to the application by setting the primary key field or property of the entity. As a special exception to this rule, if the primary key generation strategy of an entity is IDENTITY, the persistence provider is permitted to delay assignment of the primary key until pending modifications are synchronized with the database, as defined by Section 3.6.6. Indeed, when persist() is called with no active transaction, the persistence provider is required to delay generation and assignment of IDENTITY primary keys.

3.6.4. Removal

A managed entity instance becomes removed when it is passed as an argument to the remove() method of EntityManager or when the remove operation cascades from another instance to the managed instance.

Let e be an instance of an entity class. If e is passed as an argument to the remove() method of EntityManager, or if the remove operation is applied to e via cascade:

  • if e is a new entity, e itself is ignored by the remove operation;

  • if e is a managed entity, it is marked as removed and the record represented by e is scheduled for deletion from the database at or before transaction commit as a result of the flush operation specified below in Section 3.6.6;

  • if e is a removed entity, e itself is ignored by the remove operation; or

  • if e is a detached entity, an IllegalArgumentException is thrown or a failure occurs later when the flush operation occurs.

  • If e is new, managed, or removed, the remove operation is also applied to every entity t referenced by a relationship owned by e and annotated with the cascade element value cascade=REMOVE or cascade=ALL or mapped as such by the equivalent XML descriptor element.

The remove() method does not change the state held by fields of the entity instance itself.

3.6.5. Orphan Removal

The orphanRemoval member of the @OneToOne and @OneToMany relationship modelling annotations controls the enablement of orphan removal. When a relationship is mapped orphanRemoval=true, the remove operation is automatically applied to a child entity when the association between the child entity and its parent is destroyed.

  • If a managed entity instance is removed from the relationship by setting the relationship attribute to null or by removing the entity from the relationship collection, the remove operation is applied to the orphaned entity. The remove operation occurs when the persistence context is flushed, as defined below in Section 3.6.6. If an entity being orphaned is a detached, new, or removed entity, it is ignored by orphan removal.

  • If the remove operation is applied to a managed entity, the remove operation is cascaded to the relationship target in accordance with the rules of Section 3.6.4, and it is not therefore necessary to explicitly specify cascade=REMOVE for a relationship declared with orphanRemoval=true.[30]

Portable applications must not depend on a specific timing of the removal operation and must not reassign an entity that has been orphaned to another relationship, nor otherwise attempt to make it persistent, reversing the effect of orphan removal.

3.6.6. Synchronization to the Database

Usually, a persistence context is synchronized to the database as described below. However, as an exception, a persistence context of type SynchronizationType.UNSYNCHRONIZED, or an application-managed persistence context that has been created outside the scope of the current transaction, is only synchronized to the database if it has been explicitly joined to the current transaction by calling the joinTransaction() method of EntityManager, as specified below in Section 3.7.3.

Assuming that the persistence context is joined to the current transaction, and that its flush mode was not explicitly set to EXPLICIT, the state of its managed entities is synchronized to the database at transaction commit. This synchronization involves writing to the database any pending modifications to the state of persistent entities and their relationships.

A modification to the state of an entity might include an assignment of a new value to a persistent property or field of the entity, or even modification of a mutable value of a persistent property or field[31].

Synchronization to the database does not involve refreshing the state of managed entities with changes made to the database[32].

Bidirectional relationships between managed entities are persisted based on references held by the owning side of the relationship. It is the developer’s responsibility to keep the in-memory references held on the owning side and those held on the inverse side consistent with each other when they change. In the case of unidirectional one-to-one and one-to-many relationships, it is the developer’s responsibility to ensure that the semantics of the relationships are adhered to.[33]

It is particularly important to ensure that changes made to the inverse side of a relationship are reflected by corresponding changes on the owning side. The provider is not required to synchronize changes made only at the inverse end of an association. Failure to modify the owning side of a relationship typically results in the change being lost.

When a transaction is active and the persistence context is joined to the transaction, the persistence provider runtime is permitted to flush pending modifications to the database. The application can influence the timing of synchronization via the flush() method of EntityManager, by setting the FlushModeType, or by specifying a QueryFlushMode.

  • When the flush() method is called, the provider must synchronize every pending modification made to every entity currently associated with the persistence context.

  • The setFlushMode() methods of the EntityManager, Statement, Query, TypedQuery, and StoredProcedureQuery interfaces can be used to control synchronization initiated automatically by the provider.

    • The effect of FlushModeType.AUTO is defined in Section 3.15.3.

    • If FlushModeType.COMMIT is specified, synchronization occurs at transaction commit; the persistence provider is permitted, but not required, to flush at other times.

    • If FlushMode.EXPLICIT is specified, the persistence provider must never automatically flush modifications to the database.

  • The effect of the FlushModeType of the entity manager may be overridden during execution of a given query by explicitly specifying a QueryFlushMode via the setQueryFlushMode() method of Statement, Query, TypedQuery, or StoredProcedureQuery, as specified below in Section 3.15.3.

If there is no transaction active or if the persistence context has not been joined to the current transaction, the persistence provider must not flush modifications to the database.

Let e be an instance of an entity class associated with a persistence context when synchronization occurs:

  • If e is a managed entity:

    • Any pending modifications to the values held by its persistent attributes are synchronized to the database by updating the record represented by e.

    • The persist operation is applied to every entity t referenced by a relationship owned by e and annotated with the cascade element value cascade=PERSIST or cascade=ALL or mapped as such by the equivalent XML descriptor element.

    • Every entity t referenced by a relationship owned by e which is not annotated with the cascade element value cascade=PERSIST or cascade=ALL or mapped as such by the equivalent XML descriptor element is checked:

      • if t is new or removed, an IllegalStateException is thrown and the transaction is marked for rollback, or the transaction commit fails; or

      • if t is detached, the semantics depend upon the ownership of the relationship: if e owns the relationship, any changes to the relationship are synchronized with the database; otherwise, if t owns the relationship, the behavior is undefined.

  • If e is a removed entity, the record represented by e is removed from the database; no cascade options are relevant.

3.6.7. Refreshing an Entity Instance

The state of a managed entity instance is refreshed from the database when it is passed as an argument to the refresh() method of EntityManager or when the refresh operation cascades from another instance to the managed instance.

Let e be an instance of an entity class. If e is passed as the first argument to the refresh() method of EntityManager, or if the refresh operation is applied to e via cascade:

  • if e is a managed entity, the state of e is refreshed from the database by reading the record represented by e and modifying the state of e to match, overwriting any pending modifications made to the entity; or

  • if e is a new, detached, or removed entity, the IllegalArgumentException is thrown.

  • If e is managed, the refresh operation is also applied to every entity t referenced by a relationship owned by e and annotated with the cascade element value cascade=REFRESH or cascade=ALL or mapped as such by the equivalent XML descriptor element.

3.6.8. Evicting an Entity Instance from the Persistence Context

A managed entity instance is removed from the persistence context when it is passed as an argument to the detach() method of EntityManager or when the detach operation cascades from another instance to the managed instance.

Let e be an instance of an entity class. If e is passed as an argument to the detach() method of EntityManager, or if the detach operation is applied to e via cascade:

  • if e is a managed entity, it is removed from the persistence context and becomes detached;

  • if e is a new or detached entity, it is ignored by the detach operation;

  • if e is a removed entity, it becomes detached, and the scheduled removal of the record represented by e is cancelled.

  • If e is managed or removed, the detach operation is also applied to every entity t referenced by a relationship owned by e and annotated with the cascade element value cascade=DETACH or cascade=ALL or mapped as such by the equivalent XML descriptor element.

Portable applications should not pass removed entities that have been detached from the persistence context to methods of EntityManager.

Entities which referenced e before detachment continue to reference e after detachment.

Pending modifications to the state of the entity, including removal of the entity, are never synchronized to the database after the entity is evicted from the persistence context. If such pending modifications exist, an application must call the flush() method before calling detach() if portable behavior is required. A portable application must not assume that pending modifications have not been written to the database if the flush() method was not called before detach(). More information about synchronization may be found above in Section 3.6.6.

3.6.9. Detached Entities

A managed entity instance associated with a persistence context becomes detached whenever:

  • the persistence context is a container-managed transaction-scoped persistence context, as defined in Section 3.7.1, and the transaction associated with the persistence context commits, as specified in Section 3.7.4,

  • the persistence context is a container-managed persistence context, and the transaction associated with the persistence context rolls back, as specified in Section 3.7.5,

  • the entity is passed to the detach() method of the EntityManager associated with the persistence context,

  • the clear() method is called on the EntityManager associated with the persistence context, or

  • the EntityManager associated with the persistence context is closed.

A detached entity instance continues to live outside the persistence context in which it was persisted or retrieved. Its state does not remain synchronized with the database record it represents.

When an entity instance is passed to an operation like persist() or merge(), the persistence provider is permitted to use the value of the identifier and version fields or properties of an entity instance to determine whether the instance is new or detached.

3.6.9.1. Detached Entities and Lazy Loading

The available state of a detached entity instance is the state which was already loaded when the instance became detached. The application may access the available state of available detached entity instances after the persistence context ends.

The available state of a detached entity or of an embeddable object belonging to a detached entity includes every persistent field or property:

  • not explicitly mapped as fetch=LAZY,

  • accessed by the application while the entity was managed, or

  • fetched by means of an entity graph, as specified below in Section 3.12.

If the persistent field or property is an association, the available state of an associated instance may be safely accessed if and only if the associated instance is available. The available instances include every entity instance:

  • retrieved using find(), get(), findMultiple(), or getMultiple(), as specified in Section 3.6.11,

  • returned by a query or explicitly requested in a fetch join or entity graph,

  • with a persistent attribute other than the primary key which was accessed by the application while the entity was managed, or

  • reachable from an available instance by navigating associations mapped explicitly or by default as fetch=EAGER.

A persistence provider might allow access to the primary key of an unavailable associated entity.

A PersistenceException is thrown if the application accesses an unavailable attribute, collection, or entity.

3.6.9.2. Merging Detached Entity State

The merge operation allows for the propagation of state from detached entities to managed instances associated with a persistence context. Given a detached instance, the merge operation returns a managed instance with the same persistent identity and state as the detached instance, but with a distinct Java object identity.

Let e be an instance of an entity class. If e is passed as an argument to the merge() method of EntityManager, or if the merge operation is applied to e via cascade, a merged object e2 is produced:

  • if e is a detached entity, the persistent state of e is copied to a pre-existing managed entity instance e2 of the same identity or, if there is no such pre-existing managed entity, a new managed copy e2 of e is created;

  • if e is a new entity instance, a new managed entity instance e2 is created and the state of e is copied to e2;

  • if e is a removed entity instance, an IllegalArgumentException is thrown or a failure occurs later when the flush operation occurs; or

  • if e is a managed entity, e itself is ignored by the merge operation and the merged object e2 is taken to be identical to e.

  • If e is new, managed, or detached, the merge operation is also applied to every entity t referenced by a relationship owned by e and annotated with the cascade element value cascade=MERGE or cascade=ALL or mapped as such by the equivalent XML descriptor element. For every such t referenced by e, e2 is set to reference the object t2 produced by applying the merge operation to t.

  • For every entity t referenced by e via an association, navigation of the same association from e2 yields a reference to a managed object s with the same persistent identity as t.

If e has a version, as defined in Section 2.5, the persistence provider must validate that e and e2 have the same version, either during processing of the merge operation, or later when the flush operation occurs or when the transaction commits.

The persistence provider must ignore unfetched attributes of detached instances when merging. A persistence provider is permitted to report an exception if an entity instance with unfetched lazy attributes instantiated by a different persistence provider runtime is passed to merge().

When this sort of interoperability across different persistence provider runtimes from different vendors is required, the application must not use lazy loading.
3.6.9.3. Detached Entities and Serialization

A persistence provider is required to support:

  1. the serialization of detached entity instances with unfetched lazy attributes instantiated by the persistence provider runtime,

  2. subsequent deserialization in a separate Java Virtual Machine with access to the same persistence provider runtime and the same entity classes, and

  3. merging of the deserialized instances in a new persistence context implemented by the same persistence provider runtime in the second virtual machine.

3.6.10. Managed Entities

It is the responsibility of the persistence provider to ensure that at most one entity instance belonging to a given persistence context has a given persistent identity. The persistent identity of an entity class instance is represented as a pair comprising:

  1. the class of the root entity of the entity class inheritance hierarchy to which the entity class belongs, together with

  2. the value of the primary key of the entity instance, as defined above in Section 2.4.

Therefore, if the entity type X is a subclass of the root entity type Y, and x is an instance of X with primary key k, the persistent identity of x is (Y,k).

It is the responsibility of the application to ensure that an instance of an entity class is associated with at most one persistence context. If an entity instance is made managed in more than one persistence context, the behavior is undefined and unportable.

The contains() method of EntityManager determines whether an entity instance is managed in the associated persistence context. The contains() method returns true if and only if:

  • the argument is a managed entity instance associated with the given persistence context, and

  • the argument entity is not marked as removed.

The effect of cascading persist, merge, remove, or detach is immediately visible to the contains() method, whereas the actual insertion, update, or deletion of the database record represented by the entity is deferred until the flush operation occurs.

3.6.11. Entity Instance Retrieval

The interface EntityHandler, found in Section B.1 declares operations common to EntityManager and EntityAgent, including:

  • find(), get(), findMultiple(), and getMultiple(), which allow retrieval of an entity or entities—​that is, given a persistent identity corresponding to a record which already exists in the database, or a list of persistent identities, these operations return an entity instance or instances representing the corresponding record or records.

  • the methods createQuery(), createNamedQuery(), createNativeQuery(), and createStoredProcedureQuery(), which allow creation and subsequent execution of a query which returns entity instances representing records which exist in the database.

The status of an entity instance returned by an operation declared by EntityHandler, EntityManager, or EntityAgent depends on whether the operation is called on an entity manager or on an entity agent. Similarly, the status of an entity instance returned by an operation declared by Query, TypedQuery, or StoredProcedureQuery depends on whether the query object was obtained from an entity manager or from an entity agent.

  • For an EntityAgent, there is no associated persistence context, and so every entity instance returned by any operation of the agent itself, or of any query object obtained from the agent, is in the detached state. Operations on an entity agent never return the same entity instance twice.

  • For an EntityManager, every entity instance returned by any operation of the manager itself or of any query object obtained from the manager, with the exception noted in Section 4.9.2, is in the managed state and belongs to the persistence context associated with the entity manager. The instance remains in the managed state until the entity manager is closed and its persistence context is destroyed unless the instance is explicitly detached via a call to detach() or clear(), as specified above in Section 3.6.9. An entity manager is required to ensure that if an entity instance representing a given record already exists in its associated persistence context, then exactly that instance is returned by every operation that returns an entity representing the record.

When a container-managed EntityManager with a transaction-scoped persistence context is called with no active transaction, the call appears to the client to return detached entity instances, as described below in Section 3.7.2 and Section 3.15.2. However, strictly speaking, this is no more than a consequence of the extremely short lifetime of the persistence context in this scenario. From the point of view of the persistence provider, the operations of EntityManager return managed instances exactly as described here.

A retrieval operation like find() or get() accepts an entity class and a primary key value. Retrieval is by nature polymorphic, and the given entity class might be a subclass in an entity class inheritance hierarchy. Therefore, given an entity type X and primary key k, any retrieval operation must:

  1. infer the persistent identity (Y,k), where Y is the root entity class of the entity class inheritance hierarchy to which X belongs,

  2. determine if there is a database record corresponding to that persistent identity, and

  3. determine if the database record is represented by an instance of an entity class assignable to X.

If a record exists with persistent identity (Y,k) but it is not represented by an entity class assignable to X, a PersistenceException must be thrown.

Otherwise, if a record exists with persistent identity (Y,k) and it is represented by an entity class Z assignable to X, an instance of Z with primary key k is returned to the caller.

3.6.12. Load State

An instance of an entity or embeddable class is considered loaded if every attribute of the entity or embeddable class mapped (explicitly or by default) as FetchType.EAGER, including relationships and element collections, has been loaded from the database or assigned by the application. A loaded entity or embeddable object might have an unloaded attribute if and only if the attribute is mapped as FetchType.LAZY.

The available state of an entity instance and its associated instances is described above in Section 3.6.9.1.

An attribute of an entity or embedded class might also be considered loaded.

  • An embedded attribute, as defined in Section 2.7 is considered to be loaded if the embedded attribute was loaded from the database or assigned by the application, and, if the attribute references a non-null instance, the embeddable instance is loaded.

  • A collection-valued attribute is considered to be loaded if the collection was loaded from the database or the value of the attribute was assigned by the application and, if the attribute references a non-null instance of the collection type, each element of the collection is considered to be loaded.

  • A single-valued relationship attribute is considered to be loaded if the relationship attribute was loaded from the database or assigned by the application and, if the attribute references a non-null entity instance, the entity instance is considered to be loaded.

  • A basic attribute is considered to be loaded if its state has been loaded from the database or assigned by the application.

The isLoaded() methods of the PersistenceUtil interface found in Section B.24 determine the load state of a given entity or attribute of a given entity, regardless of the persistence unit with which the entity is associated, returning true if given entity or attribute is considered loaded according to the rules given above, or false otherwise.

If the persistence unit to which the entity belongs is known, the isLoaded() methods of the interface PersistenceUnitUtil found in Section B.24 and described in Section 7.11 may be used instead.

Persistence provider contracts for determining the load state of an entity or entity attribute are defined in Section 9.9.1.
